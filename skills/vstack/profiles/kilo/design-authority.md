# Kilo Design authority

Kilo Design has mixed maturity. Consume the strongest applicable source without assuming every product skill exists or is ready.

## Run order

1. Search the target repository and Kilo's discovered skills for the applicable finalized token artifact and any path-scoped `kilo-design-*` skill.
2. Treat a product skill as authoritative only when it is functioning for the target surface and its own router or repository trigger applies. Existence alone is not proof of maturity.
3. Load only the relevant overlay, reference, and recipe. Do not read the whole design repository into context.
4. Inspect every recipe's named shipped component or canonical example in the target product repository.
5. When no functioning product skill exists, use finalized token artifacts plus shipped components, nearby behavior, and host-native conventions.
6. Report missing product guidance as a coverage gap. It does not block the effort and does not justify generic UI.

## Conflict order

Use this order when sources disagree:

1. Designer's explicit approved direction.
2. Real product behavior and implementation constraints.
3. Finalized canonical tokens and generated artifacts.
4. Functioning product skill guidance.
5. Matching recipes grounded in shipped canonical examples.
6. Existing primitives and host-native conventions.
7. Nearby shipped UI.
8. General interface heuristics.

Prescriptive token drift should be named. Pattern inconsistencies require shipped evidence and designer judgment; do not normalize the whole product during a focused task.

Never install, update, finalize, publish, or write back to Kilo Design automatically.
